# Lapilli ドキュメント

Lapilli がアラートルールをどう判定するか、そしてどう動かすかを説明します。期間を決めて
`lapilli verdict` で一度だけ実行するか、`lapilli serve` で毎時実行します。同じページは
[lapilli.dev/docs](https://lapilli.dev/docs/) と
[Wiki](https://github.com/lapilli-project/lapilli/wiki) にもあります。Wiki は
docs/ を変更のたびに書き直して作る写しです。Lapilli とは何か、どうインストールするかは
[README](../../README.md) にあります。

日本語に翻訳したのは、まだ一部のページだけです（はじめに、用語集、よくある質問）。そのほかのページは英語のページにリンクしています。日本語に翻訳した後で英語のページが変わった場合は、その日本語のページにそのことを書いておきます。

## ここから始める

- [はじめに](getting-started.md)：`lapilli demo` でサンプルデータから最初のレポートを出し、次にインストールしてインシデントを 1、2 件書き留め、自分のアラートで最初のレポートを読み、そのあと `lapilli serve` で判定を続けます
- [用語集](glossary.md)：石、発火、インシデント、台帳など、これらのページで使う言葉
- [よくある質問](faq.md)：何が必要か、何を書き込むか、何をどこかに送るか
- [読み取るもの、保持するもの、送るもの](../data.md)：各コマンドが読み取るもの、`serve`
  が保持するものとその期間、誰がアクセスできるか、何をどこに送るか、何を変更できるか

## 期間を判定する

- [判定のしくみ](../how-it-judges.md)：発火とインシデントがどこから来るか、発火がインシデントを検知するのはいつか、ノイズルールと何を変えるべきか、人が何をしたか、ルールが何を加えるか、発火が来た時間帯、ニアミス、変更されたルール
- [`lapilli verdict` を使う](../verdict.md)：コマンド、出力するレポート、読み取るデータソースとその速さ、失敗するとき
- [数値の意味](../numbers.md)：各数値が何か、そして Lapilli を使わずにレポートから数え直す方法
- [ルールが発火したときに人がしたこと](../responses.md)：`--responses`、`--rollouts`、`--deploys`、発火ごとの対応、発火が役に立ったかどうかで見つけるノイズルール
- [クラウド独自のアラーム](../cloud-alarms.md)：CloudWatch、Azure Monitor、Google Cloud、OCI
  のアラームが発火したもの、Datadog のモニター、New Relic のアラート条件の判定
- [ログに対するルール（Loki）](../loki.md)：Loki に対してバックテストする LogQL のルール
- [発火がだれに届いたか、計算した値](../notifications-worked-out.md)：Alertmanager の設定から、各発火がどのレシーバーに届き、どの通知がページになるか、何が止めたかを計算します。記録ではなく計算した値です
- [バックテストは正しいか？](../check-replay.md)：`--check-replay`、バックテストと実際に発火したものの比較
- [アラートが伝える内容](../check-content.md)：`--check-content`、各ルールが発火したときに何を伝えるか、どう書かれているか

## 変更の前に

- [変更をマージする前に](../compare.md)：`--compare`、提案されたルールと現行のルールの比較、ルールに期待される水準（`--expect`）
- [CI でのプルリクエストのバックテスト](../pr-backtests.md)：アラートルールを変更するプルリクエストごとのコメントとしてのバックテストと、マージを止められるコミットステータス

## インシデント

- [ほかの場所に記録されたインシデント](../incidents.md)：記録先からコピーしたインシデントの記録と、ツールが各インシデントに関連付けたアラート
